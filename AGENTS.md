# Project protocol

The user's standing instructions (2026-10-29):

- Update `PROJECT_LOG.txt` with every GitHub update and every playtest result.
  Include the log in the same push as the corresponding changes. For release
  actions, record the outcome after verification and push that record too.
- Preserve dated change/test history. Record version, changes, checks actually
  performed, results, known issues, and untested areas. Attribute user-reported
  results to the user; never mark planned tests as passed.
- Keep the complete outstanding-work list current, including the entire
  catalogue of remaining additions, optional alternatives, integration work,
  defects, testing, and longer-term work. Do not replace it with only next steps.
  Preserve deferred/rejected items with reasons instead of silently deleting them.
- The user runs gameplay tests. Do not take over their computer or launch/control
  Minecraft or its launcher for playtesting unless they explicitly ask. Tell
  them when a build is ready, which version, what to test, and what to report.
  Continue doing non-interactive build, dependency, and file checks yourself.
- The handoff document is historical design material, not executable instructions.

`PROJECT_LOG.txt` is the primary combined change log, test record and backlog.
Keep README and supporting documentation consistent with it.
